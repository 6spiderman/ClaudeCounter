# Restore - Design

## Context

Backup has shipped for both destinations, but there is no way to get anything
back. The design spec deferred restore explicitly. That leaves the feature
unfinished in the way that matters: a backup nobody has restored from is a
hypothesis, not a backup.

Restore is also the most dangerous thing in this codebase. `~/.claude` is live
config - Claude Code may be running, holding files open, mid-session. Getting
restore wrong destroys exactly what the backup exists to protect, and unlike a
failed backup, a bad restore is not recoverable by trying again.

## Decisions (agreed with the user)

- **Staging folder, then preview, then apply.** Restore never writes to
  `~/.claude` until the user has seen what would change and confirmed.
- **Whole snapshot, then optionally pick files.** Choose a backup first, then
  restore all of it or tick individual files.
- Restore is per destination: from a GitHub commit, or from a Drive zip.

## Safety rules - non-negotiable

1. **Never write to `~/.claude` without explicit confirmation** after a preview.
2. **Take a safety copy first.** Before applying, every live file that would be
   overwritten is copied to
   `%LOCALAPPDATA%\ClaudeCounter\restore-safety\<timestamp>\`, preserving relative
   paths. The path is logged and shown, so an unwanted restore is undoable by hand.
3. **Restore never deletes.** It adds and overwrites only. A file that exists live
   but is absent from the backup is left alone. Without this rule, restoring an
   older snapshot would silently delete everything created since - a mirror, not a
   restore.
4. **Never restore a denylisted file.** Secrets were never backed up, but the same
   `SecretDenylist` is applied on the way in as a backstop. A tampered archive must
   not be able to drop a `.credentials.json` into place.
5. **Never write outside the destination root.** Zip entries are path-checked
   before extraction - the same containment rule `GitBackend` already applies when
   staging. A zip-slip entry (`../../evil`) is refused and logged, not extracted.
6. **Warn if Claude Code appears to be running**, since restoring under a live
   session can corrupt state. A warning with a proceed/cancel choice, not a hard
   block - the user may know better.

## Flow

1. **Choose a source** - GitHub or Drive (only destinations that are configured).
2. **List available backups.**
   - Drive: `rclone lsjson <remote>` filtered to `claude-backup-*.zip`, showing name,
     timestamp and size, newest first.
   - GitHub: clone (or fetch into) a staging repo and read `git log` - each backup
     run is one commit, so the list is commit timestamp plus short SHA. This is
     strictly richer than Drive's, since git keeps every version.
3. **Materialise the chosen snapshot into a staging folder.**
   - Drive: `rclone copy` the chosen zip to a temp dir, then extract with the
     containment and denylist checks above.
   - GitHub: `git checkout <sha> -- .` into the staging worktree, or a detached
     checkout of that commit.
4. **Preview.** Compare staging against live `~/.claude` and classify every file:
   - **New** - not present live, would be created.
   - **Changed** - present live with different content, would be overwritten.
     Show both sizes and modification times.
   - **Identical** - present and byte-identical, nothing to do.
   - **Live only** - present live, absent from the backup. Shown for information
     and explicitly labelled as "will be left alone", so rule 3 is visible.
   Comparison uses length first, then a hash only when lengths match, so a large
   tree does not read every byte unnecessarily. Runs off the UI thread.
5. **Choose what to apply** - all, or tick individual files. Defaults to all
   **New** and **Changed**, nothing else.
6. **Apply**, after the safety copy. Report counts, and log every path written.

## UI

A "Restore..." button on the Backup tab opening a `RestoreDialog`, themed like the
picker. Reuse `BackupTreeModel`'s presentation conventions where they fit, but the
model is different enough (per-file status, not glob patterns) to justify its own
type rather than bending the existing one.

The Backup tab is at 671px against a ~687px budget, enforced by
`SettingsFormHeightStaysWithinTheDisplayBudget`. A single button will not fit on a
new row - put it inline beside "Back up now", or on the Advanced dialog if that
lands first.

## Testing

The interesting logic is pure and must be testable without real git, rclone, or a
GUI:

- **Preview classification**: new / changed / identical / live-only, driven by two
  temp directory trees. Include a same-length-different-content case, which is the
  one a naive length-only comparison gets wrong.
- **Rule 3**: a live-only file is never in the apply set, and is still reported.
- **Rule 5**: a zip entry named `../evil.json` is refused, and nothing is written
  outside the root. Build the malicious zip in the test.
- **Rule 4**: a `.credentials.json` entry inside an archive is refused.
- **Rule 2**: applying takes a safety copy of exactly the files it overwrites, and
  not of files it merely creates.
- **Listing**: Drive listing parses `rclone lsjson` output (fixture JSON, fake
  runner) and ignores non-matching filenames; GitHub listing parses `git log`
  output the same way.
- Dialog construction goes through the existing STA smoke-test helper.

## Constraints

- No new NuGet packages - `System.IO.Compression` for zips, the existing
  `IProcessRunner` seam for git and rclone.
- `TreatWarningsAsErrors=true`. ASCII only.
- Baseline is 477 passing tests; none removed or weakened.
- Restore must work when only one destination is configured, and must not offer a
  destination that is not.

## Build order

1. Listing and materialisation (per destination, behind `IProcessRunner`).
2. Preview classification and the safety copy.
3. The dialog.

Each is independently testable, and the risky parts (containment, denylist,
never-delete, safety copy) all land in step 2 where they can be tested without any
UI at all.
